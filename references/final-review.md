# 最终审核 Playbook

所有任务 ✅ 后跑这个流程。轮数取决于体量（小 1 / 中 5 / 超大 10+）。

每轮单独：

1. 跑这一轮的检查清单
2. 列出发现 + 修复
3. 实施修复
4. 写报告 `docs/<feature>/review-round-<N>.md`（用 `templates/review-report.md`）
5. commit + push

---

## 小 (1 轮): 综合一遍

对照 **原始需求文档** + **任务列表** + **用户最初描述**，过一遍：

- 每条功能需求都实现了吗？
- 每条非功能需求都满足了吗（性能 / 安全 / 可访问性）？
- 任务列表里所有任务的 "验收标准" 都达成？
- 文档跟代码对齐吗？

修复发现的所有问题，commit。

---

## 中 (5 轮): 五个视角

每轮专攻一个视角，深度优先：

### Round 1 — 功能视角

- 每条功能需求亲自跑一遍，**不是看代码，是用**
- 边界 / 异常路径有没有覆盖？
- 用户场景一条条复盘：从用户视角能不能流畅完成？

### Round 2 — 类型 & 静态分析视角

- `tsc --noEmit` / `pyright` / `mypy` / `cargo clippy` / `golangci-lint` 全跑一遍，零 warning
- 看一遍所有 `any` / `unknown` / `as` / `unsafe` / `# type: ignore`，每个都要有理由
- 死代码、未使用的导入、未使用的变量清理

### Round 3 — 性能视角

- 数据库查询：N+1？缺索引？大表全扫？
- 前端：不必要的重渲染？bundle 体积？图片懒加载？
- 关键路径打个 profile（如果功能用户高频用）
- 内存泄漏（事件监听器、定时器、订阅没释放）

### Round 4 — 安全视角

- 注入：SQL 都用 prepared statement / ORM？输入有 sanitize？
- 鉴权：每个 endpoint 都校验？水平 / 垂直越权检查？
- 敏感数据：日志 / 错误信息 / 客户端没泄漏？token 存对地方？
- 依赖 CVE 扫一遍（`npm audit` / `pip-audit` / `cargo audit`）
- CORS / CSP / CSRF 配置

### Round 5 — UX & 可访问性视角

- 加载态、空态、错误态都好看且有意义？
- 键盘可操作（tab 顺序、focus 可见、esc 关闭）
- screen reader 朗读合理（label、aria-*、语义化标签）
- 对比度（WCAG AA）、字体大小、点击区域
- 国际化：长文本不破、RTL 不破、时区 / 货币 / 日期格式正确
- 移动端、平板、桌面三档都看一眼

---

## 超大 (10+ 轮): 五视角 + 整合扩展

前 5 轮同上，再加：

### Round 6 — 跨模块集成

- 模块边界清晰？还是悄悄耦合了？
- 接口（API、events）契约稳定吗？版本化了吗？
- 模块间的错误传播合理？

### Round 7 — 回归扫描

- 这次需求改的代码有没有影响到其他功能？
- 跑全量回归测试（如果有）
- 手动验证最常用功能仍然正常

### Round 8 — i18n & a11y 深度审计

- 全文本走的 i18n 库？还是有硬编码？
- 截屏对比 LTR vs RTL
- 用真实 screen reader（VoiceOver / NVDA）跑一遍主流程
- 自动化扫一遍（`axe-core`、`Lighthouse a11y`）

### Round 9 — 文档对齐 & 知识沉淀

- `requirements.md` 跟最终实现一致？
- `tasks.md` 备注块都写完了？
- API 文档自动生成或手写都在？
- 新人 onboarding 时缺什么？补 `README` 或 `ARCHITECTURE.md`

### Round 10 — 性能压测 & 容量

- 模拟 N 倍预期负载，找瓶颈
- 长时间稳定性（24h 跑没崩没漏内存？）
- 缓存命中率、数据库连接池、队列堆积

### Round 11+ (按需补)

- **运维与可观测**：日志、指标、追踪、告警都到位？
- **故障演练**：依赖挂了优雅降级？数据库挂了？
- **数据迁移**：老用户 / 老数据迁过来一遍演练
- **合规 & 法务**：GDPR / 隐私协议 / 用户协议 / 数据出境
- **运营准备**：客服流程、admin 工具、运营文档

每加一轮都要明确 "这一轮想发现什么"。盲目跑没意义。

---

## 多轮审核的执行节奏

```
对每一轮 R = 1 .. N:
  1. 用户已经在 Phase 0 同意走 N 轮，所以不再问 "继续吗"
  2. 跑 Round R 的清单
  3. 列出 finding（即使 0 个发现也要写）
  4. 实施修复
  5. 重新跑测试 / lint / type check
  6. 写 docs/<feature>/review-round-R.md
  7. commit "review(round-R): ..."
  8. push
  9. 立刻进入 Round R+1，不停
```

**只在最后一轮（R = N）跑完后**，向用户汇报全部 N 轮的总结。

   - 文件: `public/hero.png`
   - 修复: 转 webp，加 `<picture>` 多源

### 🟢 P2 (改进建议)
3. ...

## 修复

| Finding | Commit | 状态 |
|---------|--------|------|
